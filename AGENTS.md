# ccview-rs

A ratatui TUI to keep track of, read and use many coding-agent sessions from one screen. Claude Code is the main harness; Codex and OpenCode are secondary; more harnesses will follow, so anything harness-specific stays behind `sources/*` and the `Harness` trait. The owner wants one UI for listing, reading, resuming, forking and embedding sessions, not a Claude-only viewer. This file is the single source of truth (`CLAUDE.md` imports it). Statements marked PLANNED are not built; do not describe them as existing, and do not build them unless asked. Statements are from the code at the time of writing; if the code disagrees, the code wins and this file gets fixed.

## Architecture

Library crate (`src/lib.rs`) plus a thin binary (`src/main.rs` calls `cli::run`: no args starts the TUI; `--export <out.html|out.md|out.jsonl> [--file <session.jsonl>]`, `--live`, `--file <path>` are CLI paths without the TUI; `host` runs the background session host, `host --list` prints its sessions, `host --restore` starts the host if needed and asks it to relaunch the sessions that were open at the last shutdown; `autostart on|off|status` manages the macOS LaunchAgent).

Data flow:
- `catalog::worker::spawn` starts a source scan thread and the live thread (`catalog/live.rs`), and takes a wake callback that posts `LoopEvent::Updated` so the loop drains updates immediately. It sends `Update::{Scanned, Removed, Live, Activity, InitialScanDone}` over an mpsc channel; `App` drains it in `tick()` and rebuilds tabs and rows. Cached entries are sent before the first scan finishes.
- Selecting a session starts a follower thread (`tui/reader/follow.rs`) per `TranscriptHandle`; it sends `Batch::{Appended, Replaced, Earlier, Failed}` that `Transcript` drains. A transcript opens on its latest 200 messages (`Replaced`, with the cursor of what is not loaded); `App` asks for the previous page (`request_earlier`) whenever the last drawn viewport was within a screenful of the top and a cursor exists, and a landed page is prepended with the scroll position moved by the lines it added, so the reader stays on the same line. An `Earlier` whose requested cursor is no longer the conversation's cursor (file replaced meanwhile) is discarded. `App::refresh_preload` hands `Transcript` the wanted list on every row refresh: every active session (`tabs::entry_is_active`, Active-tab order) first, then the top 8 rows of the current tab, Rollout handles only. `Preloader` loads only the first page of each (the same 200 messages and cursor the pane would show after its first batch) on short-lived background threads (at most 2 at once, thread priority lowered, cancelled when `Transcript` drops) straight into the LRU behind the entries the owner used; it starts nothing while the cache (sessions plus in-flight loads, or 6000 messages) is full, never loads the shown or targeted session, and tries each wanted key once until it leaves the wanted list. A preloaded entry is shown at once, at the bottom, when selected, then revalidated by a follower whose `Replaced` batch carries a fresh cursor for paging up.
- Embedded sessions live in the session host daemon (`terminal/session_host/daemon.rs`), not in ccview. `SessionManager::launch` sends `Spawn` (the client's whole environment, minus `TERM`/`COLORTERM`, which the host sets) and then opens one connection per session with `Attach`: the daemon replies with the screen as `state_formatted()` bytes plus a `ModeSnapshot` (kitty keyboard stacks, focus reporting, synchronized output, title) and then streams the raw output chunks that arrive afterwards, snapshot and subscription taken under the parser lock. The `RemoteHost` keeps its own vt100 parser and `Responder` (events and modes, replies go to a sink). Input and `Resize` flow back on the same connection through a bounded queue (256 messages, input in 64 KiB frames) drained by a `remote-writer` thread: `RemoteHost::write` never blocks the UI thread, a full queue drops the input and returns `WouldBlock`, and a failed or timed-out socket write (which can leave a frame half written) marks the pane standby for good. In the host, input to the PTY and `Responder` replies go through one queue (256 chunks) drained by a `pty-writer` thread, so a child that stops reading its tty blocks only that client's input thread, never the reader thread holding the parser lock (replies are dropped when the queue is full); the registry lock is held only to clone `Entry` values, never across `Entry::info` or a screen snapshot. On startup `SessionManager::attach_existing` attaches every session the daemon lists, with `yield_if_held`.
- One active client per session (`daemon.rs` `Lease`, token per attach). Only the holder's input and `Resize` reach the PTY; the daemon drops the rest, whatever the client does. `Attach` takes the lease (newest wins: startup, launching, `r`, `c`, Enter in a standby pane), so opening a second ccview puts the first one's sessions on standby. The previous holder receives `Response::Demoted` and its `RemoteHost` goes standby: it writes and resizes nothing, the pane shows `attached in another ccview · press Enter to take over` instead of the mirror, keys other than the `^Space` prefix actions and Enter are dropped. Enter re-attaches at the pane's size (`SessionManager::take_over`) and demotes the other. The holder's detach or disconnect frees the lease; standby clients are never auto-promoted.
- Each embedded session (`PtyHost` or `RemoteHost`) has a waker that sends `LoopEvent::Output(id)` to the event loop, so output redraws without polling. Input is read on its own thread (`LoopEvent::Input`) with `crossterm::event::read` over crossterm's `use-dev-tty` event source (see Known limitations). The loop draws at most every 16 ms and polls every 50 ms when idle.

## Safety rules

These are hard. A test or tool that breaks one is a bug.

1. Never start a real `claude`, `codex` or `opencode` from tests or tools. Point `CCVIEW_CLAUDE_BIN`, `CCVIEW_CODEX_BIN`, `CCVIEW_OPENCODE_BIN` at a fake script or `/usr/bin/false` (as `tests/harness_launch_pty.rs` does).
2. Tests never write to `~/.claude`, `~/.codex`, the OpenCode database, `~/.config/ccview-rs` or `~/.cache/ccview-rs`. Use a temp dir and override `HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_DATA_HOME`. Unit tests construct `Favorites`, `Identity`, `ViewSetting` and `IndexCache` with explicit temp paths; never call their `load_default`.
3. Never open a GUI app or terminal window from tests. `harness::external_terminal::open_with` takes an opener closure; inject a fake.
4. The only `claude` subcommand ccview runs on its own is the read-only `claude agents --json`. Never run `claude agents` interactively, `claude attach` or `--bg` from tests or tools. `attach` exists only as a user-triggered launch (key `a`).
5. OpenCode's database is opened with `SQLITE_OPEN_READ_ONLY` and `PRAGMA query_only = ON` (`sources/opencode.rs::open_read_only`). Keep it that way; use no other open path.
6. Session transcripts are private data. No transcript content in reports, logs, commit messages or fixtures. Fixtures are synthetic (`/work/app`, short invented prompts). The search index (`search-v1.sqlite`) holds every token of the indexed transcripts; treat it like the transcripts: tests use a temp cache dir, and a scratch database built from real data is deleted at once.
7. No customer or personal names in code, fixtures or docs.
8. A test that can start a session host must set `CCVIEW_RUNTIME_DIR` and `XDG_STATE_HOME` to temp directories (the host writes `sessions.json` to the state dir) (every binary-running test does, so none ever attaches to the owner's real sessions), and every test that runs the UI binary must set `CCVIEW_NO_SELF_UPDATE=1` unless it is the self-update test, which only touches a binary it copied into a temp dir, must stop the daemon and its sessions when it ends, including on failure (`tests/common/mod.rs` `RuntimeGuard`), and must leave no process behind (check `ps`), and must give every host it can start the lifeline (`CCVIEW_HOST_OWNER_PID` = the test process pid, via `tests/common` `with_lifeline`/`lifeline`) so a killed test run cannot leave a host or its fake children alive. Test temp directories named `ccview-<...>-<pid>` (the pid is the last all-digit segment after the first) are swept once per test process when older than 10 minutes, owned by this user and their pid is dead (`tests/common/stale_temp.rs`, also compiled into the lib for unit tests). Daemon unit tests run `daemon::run` in a thread with an explicit `RuntimeDir`. The user-triggered stop is `sys::process::terminate` (SIGTERM, one pid, never SIGKILL, never a group), reached from `d` after the stop confirm and from the host's `Request::Stop`; the only other signalling is `PtyHost`'s own teardown of the child it spawned (SIGHUP, then SIGKILL of that child's process group, in `terminal/host.rs` `drop` and `kill`); `Dismissed` and `dismiss.rs` never signal. Tests signal only processes they spawned themselves (a `sleep` child or a hosted `sleep`), never a pid from a real registry: they set `App::claude_sessions_dir` (or `CLAUDE_CONFIG_DIR`) to a temp dir. Besides that, only `RuntimeGuard` signals processes (and the restore tests, which send SIGTERM to their own temp daemon).
9. Nothing in tests, scripts or tooling may run `ccview-rs autostart on` (or `off`), call `launchctl`, or write to or read from the real `~/Library/LaunchAgents`. `terminal::session_host::autostart::Agent` takes its directory, log path and uid explicitly and `Launchctl` is a trait; tests use a temp directory and a recording fake. Only the user-triggered CLI command and the settings row use `SystemLaunchctl`, and no test presses that row.

## Layout and style

- Module files are `foo.rs` next to `foo/`, never `mod.rs`.
- A directory holds at most about 12 entries; split by concern before it grows past that.

Persisted files go through `store`. Each harness's binary name and its `CCVIEW_*_BIN` override live in `sources/<harness>`; `harness` only assembles argv from them.
- `unsafe` lives in `sys/` and `terminal/host.rs` only.
- Every change passes `cargo fmt --all --check`, `cargo clippy --all-targets` and `cargo test`. `Cargo.toml` `[lints.clippy]` warns on `too_many_arguments` and `large_enum_variant`; `cargo clippy --all-targets` is clean, keep it that way (`footer::draw` takes a `FooterView`, `Request::Spawn` boxes its `CommandSpec`).

## Code conventions

- Simplest valid solution. No abstraction nobody asked for. Fix root causes, not symptoms.
- No code comments. Make the code clearer with names, constants and small functions. The only exception is a constraint imposed from outside the file. Rationale goes in the commit message.
- `session::transcript::Message` and `Block` are the shared shape every harness converts into (`sources/claude/transcript.rs`, `sources/codex.rs`, `sources/opencode.rs`). Do not change them casually; a change touches all converters, the renderer and the exporter.
- Tests: see Test policy below.
- No new dependency without a stated reason in the commit. Current set is in `Cargo.toml`.
- Performance budget: no file or process IO on the UI thread (scanning, following, `claude agents --json` and the search indexer run on their own threads, the indexer at background priority); per-frame work is cached (conversation lines per width and level, tab and row lists on change); keep frame time in the hundreds of microseconds; opening a transcript reads only its tail (about 200 messages), older messages are paged in on scroll, and the loaded window is capped at `MAX_LOADED_TURNS` (20,000 turns): paging stops there, and a live append that takes the window past the cap by 500 drops the oldest turns; either way the top line says `earlier messages not loaded`.

## Test policy

A test exists to fail when a behaviour a user or a safety rule depends on breaks. Write down that intent in one sentence from outside the code (a bug report, a safety rule above, a product decision above) before writing the test; if you cannot, do not write it.

Test:
- Outcomes: what the user sees or loses, what reaches the child process, what is written to or never written to disk, what is refused. The near-miss a lazy implementation gets wrong (the 95% lineage boundary, a hostile cwd, a truncated file, a corrupt config) is the test, not a branch that merely exists.
- A table only when its rows are named cases and each drives a different branch.

Do not test:
- Frame or footer text, titles, labels, wording, layout at widths, key-table contents, colours or constants. Exception: at most one or two layout-hazard tests per rendering feature, where a bug would hide data or break the screen (one accent per zone, no identity bar on inactive rows, no `Loading` placeholder once something was shown, no markdown line wider than the pane).
- Anything that iterates the production constant or table it checks, so a wrong constant passes.
- Private functions, internal struct shape or intermediate values: a correct refactor must not break the test.
- Code that merely forwards, defaults, enum members, or what an end-to-end PTY test already asserts. Do not repeat a persistence round trip per store; one corrupt-file-loads-empty test per store is enough.
- Wall-clock assertions except a stated performance budget.

Size:
- A bug fix gets one regression test. A feature gets a few tests on its core behaviour. A rendering feature gets at most one or two layout-hazard tests. Do not add tests beyond that, and do not add tests nobody asked for.
- Prefer one PTY test (`tests/*_pty.rs`, fake binaries only) for a flow across modules over several unit tests of its parts.

Before keeping a test, break the behaviour it guards in a throwaway copy of the worktree (negate the condition, drop the branch, return early, widen a match) and confirm the test fails; reverting the whole diff proves nothing. `cargo-mutants` is not installed, so apply one textual mutation per run, run `cargo test --no-fail-fast`, record which tests failed, restore. A test that no targeted mutation fails is deleted; a mutation that no test fails is reported as a gap, not patched with a new test unprompted.

## Product decisions already made

- Focus model: three zones, `Focus::{List, Conversation, Embedded}`, one focused at a time (focused border and title marker; others dimmed). The right pane shows the embedded session if one is bound to the selected entry, otherwise the transcript.
- Keys, list and transcript: the list has two sub-focuses. In the rows `Right`/`l`/`Enter`/`Tab` focuses the right pane, `Up` from the first row moves to the tab bar, `x` hides the selected session (persisted in `hidden.json`, never touches transcripts), `H` shows hidden sessions dimmed, `S` stars the selected row's directory, `E` toggles `expand copies` (in memory only, not persisted). On the tab bar `Left/Right`, `h/l` or `[ ]` switch tabs, `s` stars or unstars the active directory tab and `Down`/`Enter`/`Esc` return to the rows; `Left`, `h`, `Esc` or `Tab` in the transcript returns to the list; `Ctrl+C` or `q` quits, with a confirm only while embedded sessions are running. `Shift+Left/Right` switch tabs from the rows, the tab bar and the transcript (no wrap change; inside an embedded session the child gets them). Actions: `r` resume, `f` fork, `n` new, `c` continue, `a` attach (Claude only), `o`/`O` external terminal, `s` or space star, `i` toggle important, `w` toggle on hold, `C` cycle colour, `v` cycle verbosity.
- Keys, embedded: everything is forwarded to the child, including `Ctrl+C`. The only interception is the `^Space` prefix: `^Space l`/`Esc` back to list, `x` or `d` detach (no confirm, the session keeps running), `[`/`]` or arrows previous/next session, `PgUp/PgDn` or `Up/Down` scroll the child, `C` colour, `^Space ^Space` sends a literal `^Space`. An unknown key after the prefix is dropped. A key press on an exited session dismisses it.
- Verbosity levels `chat`, `tools`, `everything`, cycled by `v`, persisted in `view.json` (default `tools`). `chat`: user prompts and assistant text, plus a dim `· N tool calls` line for each run of hidden calls. `tools`: the Claude Code look, with tool calls, collapsed results and diffs, and thinking collapsed to three lines. `everything`: full untruncated results and diffs (wrapped, not cut), thinking in full, the rest of a multi-line Bash command and an Agent's prompt under its call, and system/meta records. The transcript has no identity gutter; the identity colour tints the pane border and title.
- Identity colours: 14 hues (`tui/style/palette.rs`), a stable default from a hash of the session id, no two tracked sessions share a hue while free ones remain, overrides persisted in `colors.json`. Colours are tracked for running embedded sessions and sessions with a live pid, and the list bar is drawn only on those active rows.
- Mouse capture is on by default (`mouse` in `ui.json`, default true) so the divider can be dragged and the wheel scrolls the pane under the pointer; with `"mouse": false` capture is on only while a running embedded session is focused and that session enabled a mouse protocol or the alternate screen. The wheel is forwarded to the child, or turned into arrow keys on the alternate screen (3 lines per notch). With capture on, the terminal's own text selection needs the Shift (or Option in iTerm) modifier.
- Links: bare `http://` and `https://` URLs anywhere in the transcript (assistant markdown, code spans and blocks, user prompts, meta text, thinking, tool results) and Markdown `[text](url)` links are drawn blue and underlined, and a plain left click (press and release on one cell, no drag) opens the URL in the default browser with `open`; the notice is `opened <host>`. A Markdown link shows only its text (the whole text is the link) when the URL is http(s); other schemes (`file:`, `javascript:`, relative paths) are not links and keep the old ` (url)` suffix, and images keep it too. The text shown can differ from the URL it opens (that is what a Markdown link is); the notice names the real host. A URL wrapped over several rows is clickable on every row. Copying a selection copies the visible text, so a Markdown link copies its text, not its URL. Embedded panes: a plain click (no drag) in a running pane whose child has no mouse protocol opens the http(s) URL found in the pane's screen text under the cell (the text is not drawn differently; there is no hover feedback); rows joined by vt100's soft-wrap flag count as one line, so a URL the terminal wrapped is clickable on every row and opens in full; a child that enabled a mouse protocol gets the click as before. A URL the child broke with its own newline or cursor movement (no wrap flag) is only found up to the row end. Not covered: the tool header summary, tool detail lines and diff rows (not linked), keyboard activation, hover feedback, a `file:` or `mailto:` scheme.
- Text selection: a left-button drag in the transcript text area (not the border) or in a running embedded pane whose child has no mouse protocol highlights the cells (reverse video) and copies on release through OSC 52 (`outer_terminal::clipboard_sequence`, target `c`, 100 KiB cap, notice `copied N characters`). The transcript selection is kept in line/column coordinates of the rendered lines, so it survives scrolling and is dropped on resize, view-level change or a different session; the copied text is the rendered lines (not markdown, and including the `> `, `● `, `⎿` and indent prefixes as drawn), one `\n` per visual line, trailing spaces trimmed. The embedded selection is in screen cells, copied from the current screen at release (vt100 joins wrapped rows). Esc, a click elsewhere, a key sent to the child or the child's scrollback wheel clears it. Not built: auto-scroll while dragging past the pane edge, word and line selection by double and triple click, a `pbcopy` fallback (terminals without OSC 52, such as Apple Terminal, copy nothing). A child that enabled a mouse protocol gets the mouse as before; Shift-drag is then the terminal's own selection.
- Claude launches (new, resume, fork, continue) set `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` unless the `disable_agent_view` setting is off, and remove a named list of inherited session-identity variables (`CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `_ENTRYPOINT`, `_EXECPATH`, `_MESSAGING_SOCKET`, `_MESSAGING_TOKEN`, `_SESSION_ATTENDED`, `_SESSION_ID`, `CLAUDE_PID`) so a nested session does not believe it is inside another; user-set variables such as `CLAUDE_CODE_USE_BEDROCK` are kept, and `CLAUDE_BG_*` variables are not stripped. `attach` is the exception: it keeps the environment.
- Refresh cadences: registry stat every 250 ms (`catalog/live.rs`), `claude agents --json` on change (min gap 500 ms) or every 5 s, sub-agents every 500 ms, source rescan every 1 s (`catalog/worker.rs`), transcript follow poll 500 ms, transcript settle delay 120 ms (applied only when the previous selection changed less than 120 ms earlier and the target is neither shown nor cached; otherwise the load starts on the next tick), frames at most every 16 ms.
- Ordering: `SessionEntry::last_used` is the recency key everywhere (catalog sort with path as tiebreak, the relative time in the row, lineage's choice of the visible member). It is the timestamp of the last genuine user message, not the file mtime, because mtime is also bumped by background agents, sub-agent output, title regeneration and other appends. Claude: the last `type:"user"` record that is not `isMeta`, not `isSidechain`, not a tool_result carrier and not a wrapper text (`<`, `[Request interrupted`, `Caveat:`: the `genuine_prompt` predicate, `scan.rs` `genuine_turn`), using its RFC 3339 `timestamp` (`sources::millis_from_rfc3339`), derived in `extend_record` from the appended bytes only (the last 8 user lines of an append are examined, as for `last_prompt`) and stored in `FileMeta::last_user_message_ms`. Codex: the last user `response_item` message that is not a wrapper (`<`, `# AGENTS.md`) within the last 512 KiB of the rollout. OpenCode: `max(message.time_created)` of the session's `user` messages. A session with no genuine user message (or an unparseable timestamp) falls back to the file mtime (Claude, Codex) or `time_updated` (OpenCode). Nothing else needs the mtime on `SessionEntry`: index freshness uses size plus mtime in the index record, and the age limit works on the file mtime before parsing. `tui/widgets/tabs.rs` `session_indices` is the one place that orders a tab: a stable sort over the catalog order (recency descending) whose keys are, in this precedence, needs-you (Active tab only), important, starred, then (Active tab only) the rank needs-you 0, busy or running agents 1, idle 2, on hold 3 (an on-hold session takes rank 3 unless it needs you, and the needs-you key already puts a blocked one first); ties keep recency order. All, Favorites and directory tabs therefore show important sessions, then starred, then the rest, each by recency. The Active tab (every active session, the same test as the colour bar, `tabs::entry_is_active`: a live process or an activity entry, idle ones included, and not dismissed) shows needs-you (blocked) first of all, then important, then starred, then busy before idle before on hold, each group by recency. A lineage counts as starred or important if any member is. An important idle session stays on top while other sessions are used, but never buries a session that needs the owner. The selection follows its session path, so it stays on the same session when a rescan moves it. In every tab the sort key is, in order: needs-you (Active tab only), important, starred, active (`entry_is_active`, the colour-bar test: active sessions sit above inactive ones, so a newer idle session never buries a running one), manual position, then the Active-tab attention rank. Manual order therefore orders sessions only within the same class; ids in the tab's list in `order.json` (`ManualOrder`, key `TabKey::storage_key`) form a block in that order below every session of the same class that is not in the list, so a session started after the last drop shows at the top of its class. An id in the list that is not in the tab (other directory, hidden, aged out, gone) is ignored and kept in the file, so it takes its place again when it returns. The id used is the visible member's (a collapsed lineage is one row).
- Manual order: a left-button drag on a list row (any tab) picks it up; it is a click (select) until the pointer leaves the press row. While dragging, the dragged row is highlighted and a rule marks the drop slot (on the blank line between rows; at the very top it is drawn over the tab bar line); a drag event on the first or last visible line, or outside the rows, scrolls the list one row per event (a stationary pointer does not keep scrolling). Dropping onto the row's own position does nothing. A drop writes the tab's whole visible order to `order.json` (ids listed there but absent from the tab are appended so they keep their place for when they return). `Esc` cancels a drag. `Alt+Up`/`Alt+Down` (rows focused) and `K`/`J` move the selected row one step and persist the same way; `R` clears the current tab's manual order (notice `order reset`). Help-only key table entries. The drag does not touch the transcript or embedded copy selection (`input/copy.rs`).
- Important: `i` (list rows and transcript, not the tab bar, not inside an embedded session) toggles an `important` flag, separate from stars: it changes order only, no tab. Persisted in `important.json`. A lineage counts as important if any member is, and `i` clears all members or flags the visible one (same rule as stars). Marker: a bold `!` (theme `important`) right before the row title, after the status dot and the needs-you chip; the title gives up two columns on those rows. Help-only key table entry.
- On hold: the owner's sessions often wait on colleagues or reviews, which no registry or transcript signal shows, so `w` (list rows and transcript, not the tab bar, not inside an embedded session) toggles a manual `on hold` flag (notices `on hold`, `on hold cleared`). Persisted in `on_hold.json` with the time it was set; the object leaves room for a reason later. Lineage as important (any member counts, `w` clears all members or flags the visible one). Only two things clear it: `w` again, or the owner replying: `OnHoldSessions::reconcile` on every catalog update clears an id when the entry for it (its `session_id` or one of its `copies`) has `last_used` strictly later than `since_ms`. Going busy alone does not clear it (the session may be working on something else while still waiting); an id missing from the catalog is kept. Independent of dismiss, important and stars: `d`/`D` never read or clear it. Held ids join the age-limit keep set, so a long wait does not age the session out. Effect: Active tab only, on hold ranks below idle (see Ordering); the Active count still includes held sessions; no new tab. Row: when the session is idle or has no status, the status word reads `on hold` instead of `idle` and the dot is `theme::on_hold()` (muted violet); when busy or blocked the real state shows and `on hold` follows as an extra part. No title marker. Help-only key table entry.
- Asks you (INFERRED, a heuristic, not a signal): Claude's registry says only `idle` when a turn ends on a question; nothing machine-readable marks it. `sources/claude/asking.rs` `asks_user_after` folds over every transcript line in `extend_record` (no new IO, stored as `FileMeta::asks_user` in the index and copied to `SessionEntry::asks_user`). A session asks when the last genuine record, ignoring sidechain, `isMeta` and `tool_result` user records, is an assistant line with `stop_reason` `end_turn` whose last content block is text, and the last paragraph of that text (blank-line split, after removing fenced code blocks) contains a `?` outside backtick code spans and outside `://` urls, or a line beginning `Decision for you:` (leading `*_>#-` and spaces ignored). Any later user message (including an interrupt notice) or any other assistant line clears it, by rescan. Shown only while the activity is `idle` with no running agents, not on hold, not dismissed: the detail line status word reads `asks you` and the dot take `theme::asks_you()` (indexed 161, next to the attention red 196) instead of `idle`; the Active tab ranks it after needs-you and before busy and agents (`attention_rank`; on hold still sinks to the bottom, and important/starred/manual order still come first). Not counted in the footer summary or the tab counts: `Summary` is built from activities only and does not see entries. Codex and OpenCode: always false. Expect false positives (a rhetorical question in the closing paragraph) and false negatives (a request phrased as a statement, or a question in an earlier paragraph); the heuristic reads the assistant's prose, never a user-facing signal.
- Stale: a session that is `busy` with no running sub-agents, not on hold, whose `Activity::last_activity` is at least `STALE_AFTER` (30 min, `session/activity.rs`) old is probably stuck or looping. `last_activity` is the later of the registry `statusUpdatedAt`/`updatedAt` and the transcript file's mtime; the mtime is read by `Tracker::compute` on the live thread (one `stat` per busy session per activity refresh), never on the UI thread. Row: the status dot takes `theme::stale()` (amber) and the detail line gets a part `quiet 47m` right after the status (`m`, `h` or `d`, whole units), so the title width does not change; clipped from the right like every detail part. A session on hold, dismissed (not in the activity map), idle, blocked (needs you) or with running agents shows no stale marker. No ordering change: the Active tab ranks it as busy, and needs-you still comes first. No setting, no key.
- Shared checkout: two or more running (`pid_alive`), non-dismissed sessions that are active at the same moment (busy, blocked or running sub-agents; idle sessions never count, so a repo with many idle sessions shows nothing) of different conversations whose cwd resolves to the same checkout risk overwriting each other's edits. The checkout is the nearest ancestor directory holding a `.git` entry, a directory or a file, so a git worktree (`.git` file) is its own checkout even when it sits inside another checkout's tree, and a cwd with no `.git` ancestor has no checkout and is never flagged (a folder holding several repositories is not one working tree). The `.git` walk (a few `stat` calls per cwd, cached per cwd while a session with it runs) runs on the live thread in `CheckoutResolver::resolve` whenever the registry changes; the catalog receives `Update::Checkouts` and derives `SharedCheckouts` (in `derive_activity`, so dismiss, live and merge changes recompute it) with no IO. Lineage copies of one conversation (same `copy_of` group) never count against each other; on a collapsed lineage the visible row shows the flag of any member. Row: the detail line gets a bold amber part `shares checkout with <other title>` (title cut to 24 columns, `+N` appended when more than one other session shares it; the first other is the most recently used), after the status and flags and before directory and time, so a narrow row clips the right end first; no title marker, no ordering change, no key, no setting. A session on hold still counts (it is running).
- Dismiss and stop: `d` (list rows and transcript, not the tab bar, not inside an embedded session) stops the selected active session and removes it from the active set; `D` undoes the dismissal only (a stopped session does not come back, so `D` matters for a dismissal of a process that still runs). Stopping is irreversible, so `d` first shows `stop <title>? y/n` in the footer (`Confirm::Stop`; any key other than `y`/`Y` cancels, nothing is signalled and nothing is dismissed). Stopping is SIGTERM to the session's own process, never SIGKILL, never a group. Targets, in order: (a) a row bound to a running hosted embedded session: `Request::Stop { id }` to the session host, which SIGTERMs that session's child only, refuses ids it does not own (`no session <id>`) and leaves the host and its other sessions running; (b) a live session ccview does not own: SIGTERM to `entry.live.pid`, only if the pid is alive, `<claude config>/sessions/<pid>.json` still names this session id and its `procStart` (a UTC `ps -o lstart` string, whitespace-normalised) equals the live process's start from `sys::process::process_start`; a missing `procStart` refuses (pid-reuse guard; on a mismatch nothing is signalled, the notice says so and the dismissal is still recorded); (c) a session with no pid (Codex, OpenCode, activity-only): dismissal only, no confirm, notice `no process to stop`. Then the dismissal is recorded as before. A dismissed session looks inactive everywhere (colour bar, Active tab and its count, rank, status text, badges): `Catalog::derive_activity` drops it from the effective activity map and `tabs::entry_is_active` and the list row consult `Catalog::dismissed()`. The dismissal is stored with the pid (0 for a session with only an activity entry) and `Dismissed::reconcile` clears it on every catalog update, once both a live and an activity update have arrived, when its current pid differs from the stored one (new run or process gone), or when nothing active is left; a session stays dismissed whatever it is doing (idle, busy, blocked, running sub-agents), across restarts while the pid lives. A session id with no entry in the catalog is left alone. On a row bound to a running embedded pane the pane stays in the strip, showing the exited state once the child ends. The dismissal's own identity is the pid only; the start time is checked only before signalling. In a collapsed lineage it acts on the visible member and its lineage-effective live and activity.
- Maximum session age: sessions whose last activity is older than `max_age_days` (default 30; choices 7, 14, 30, 60, 90, 180, 365 days or all, stepped with Left/Right; a hand-edited value such as 45 is honoured and the next step snaps to the neighbouring choice) are not loaded at all, not just hidden. The cutoff is the file mtime (Claude transcripts and Codex rollouts) or `time_updated` (OpenCode), never the session start or the displayed `last_used`, because it must be decided before any parse: Claude `list_files_within` and Codex `list_codex_files_within` drop old files at the directory listing, OpenCode filters in the SQL `WHERE`, and the persistent index and the cached first-frame entries drop them too, so the index does not grow with dead sessions. Always loaded regardless of age (the keep set `App::age_filter` hands the scan thread): starred sessions, important sessions, sessions with a live process or an activity entry, sessions bound to an embedded pane (running or exited, still in the strip) and the selected session. The ids are matched without parsing: a Claude id is the file stem, a Codex id is the suffix of the rollout file name (`rollout-<timestamp>-<id>`), an OpenCode id is the `session.id` column. Changing the setting, or un-starring or un-flagging an old session, takes effect on the next scan (immediately for the setting): a lowered limit removes rows, a raised one scans what was skipped. A session that is hidden by age cannot be starred or flagged since it is not listed. Lineage: ancestors outside the limit are simply not loaded; a collapsed row whose newest member is inside the limit stays. OpenCode is rescanned only when its database changes (or the limit does), so an OpenCode row ages out at the next database change, not on the clock. Sessions that are live at startup are asked for after the first live update, so an old live session may be skipped and rescanned once within about a second.
- Transcript loading: tail-first and paged. `JsonlFollower` (Claude and Codex JSONL) never reads a file from byte 0 on open: the first poll records the end of file, finds the last line boundary, reads backwards in chunks (256 KiB doubling to 4 MiB, the incomplete leading fragment carried into the next earlier chunk) until about 200 messages (`INITIAL_MESSAGES`) are parsed, and sends a `Replaced` with the cursor of the earliest line read; the live follow starts at that last line boundary, so a message appended during the read arrives once and an unfinished last line waits until complete. Older messages arrive only when the viewport comes within a screenful of the top: `Earlier` batches of `PAGE_MESSAGES` (200), prepended with the scroll position moved by the lines added. Truncation or a replaced file reloads the tail. OpenCode does the same by `(time_created, id)` rows with `PRAGMA query_only`; its fingerprint poll reloads from the loaded window's floor. A tool result whose call is on an unloaded page renders as an orphan result until that page is prepended, which re-attaches it. The window is capped at 20,000 turns (see Performance budget).
- Self-restart on update: the owner installs with `cargo install --path . --locked` while a UI is open, so the UI watches its own executable (`current_exe` resolved through symlinks at start; a stat every 2 s from `tick`) and, when the inode, mtime or length differs and the new stamp has stayed the same for a poll after it was first seen (cargo writes then renames), saves `ui_state.json`, resets the terminal modes (`outer_terminal::leave`) and raw mode but stays on the alternate screen (no `\x1b[?1049l`, so the owner never sees the normal screen between the two processes) and `exec`s the same path with the same argv; the new process, finding the state file, keeps the old frame on screen until the restored selection is applied (at most 300 ms, then it paints what it has), then writes the clear of the inherited alternate screen (`ESC[2J`, no cursor-position query) and its first full frame inside one synchronized update (DEC 2026, `tui/frame.rs`; terminals without it ignore the sequences), so the swap is a single repaint; every later frame is wrapped in a synchronized update too (re-entering the alternate screen does not clear it); if the `exec` fails, `ratatui::restore` runs and the error is returned as on any failed start. A file that is not a regular executable file with a length above 0 never triggers it. It restarts only when focus is not `Embedded` and no confirm, overlay or row drag is open; in an embedded session the footer says `update ready: leave the session to restart` and the restart follows once focus leaves. With `auto_restart_on_update` off (settings row `Restart on update`) the footer says `update ready: restart ccv` and nothing restarts. A UI that was itself started by a restart (it found a fresh `ui_state.json`) does not restart again within 10 s of its start and shows the same notice, so a bad install cannot loop; a failed state save also cancels the restart with a notice. The new process restores the tab, the selected session, the focus zone (list or transcript, never an embedded pane), `show_hidden`, the expand flag and the transcript scroll once the catalog and transcript are loaded, ignoring ids no longer present. Embedded sessions live in the session host and are reattached at start; the host is not restarted.
- Launching a session already open in an embedded pane asks for confirmation (`Confirm::Duplicate`). `r` (embedded) first looks for a running pane, then for a running host session, bound to any member of the row's lineage group (`Catalog::lineage_ids`: the row's id plus every other member, collapsed or expanded), so a resume that rebound the pane to a newer id, or a pane started from an older copy, is shown again instead of a second one being spawned; the host match also accepts the row's live pid. `n` and `f` always spawn.
- `c` (continue latest) never starts a second copy: when a running session started with continue exists for the same harness and directory (title prefix `continue · `, matched in the panes and in the session host's list), it is attached and shown instead and the footer says so. `n` always starts a new session.
- Split: the list/detail ratio (default 0.35, list at least 24 columns, detail at least 30) is persisted in `ui.json`; resize with `<` `>` `=` (prefix first inside an embedded session) or drag the divider; mouse capture is on unless `mouse` is false in `ui.json`.
- In an embedded session `Left` returns to the list only when the cursor is visible and nothing but prompt glyphs, box drawing or whitespace is left of it (`tui/embedded/back_to_list.rs`); Ctrl+C is always forwarded; a child that exits 0 returns focus to the list automatically.
- The running-sessions strip (hidden by default; the `sessions_strip` setting draws it as a one-row line above the panes, and when off the panes take that row; embedded sessions, `1`-`9`, bells and the footer chip work the same either way), the transcript and session pane titles and the footer chip name the harness (`claude`, `codex`, `opencode`); list rows do not. In a row's detail line the status (`idle`, `busy`, badges) comes first so it is not clipped.
- Overlays: `,` opens settings and `?` opens help in the list, tab bar and transcript; inside an embedded session they are `ctrl+space ,` and `ctrl+space ?`. While one is open it owns every key (Esc closes, or leaves the hidden-sessions sub-list); a click outside closes it, the wheel scrolls it. Settings, all applied at once and persisted: identity colours on/off plus a colour picker for the selected session, view level, mouse capture, split ratio and reset, terminal app for `o`/`O` (auto, Terminal, iTerm, Ghostty, WezTerm), hidden sessions (Enter un-hides), disable Claude agent view, `Sessions strip` (on/off), `Load sessions from the last` (the maximum session age, see below).
- Footer: shows only each zone's essential hints plus `, settings`, `? help`, `q quit`; `help` and `quit` are pinned so they survive narrow widths. `C`, `v`, `< > =`, `f`, `c`, `a`, `o/O`, `x`, `H`, `g/G`, PgUp/PgDn work as before but are listed only in help.
- Starred directories (`s` on the tab bar, `S` on a row) sit first among the directory tabs with a `★ ` label prefix, each group most-recent-first; `s` on the tab bar acts on the directory, not the session.
- Lineage: resuming, continuing or backgrounding a Claude session writes a new JSONL that starts with the whole earlier history while the old file stays. Only records starting with `{"parentUuid"` carry a top-level `uuid`; each file keeps a bottom-128 sketch of 32-bit hashes of those uuids (exact for files with fewer than 128). Two files are compared over the sketch values at or below the smaller of their two cut-offs. If fewer than 8 values fall there, or none are shared, they are unrelated. A side is contained when at least 95% of its values are shared: one side contained means it is the ancestor of the other, both contained means identical copies (older is the ancestor), neither means a fork and both stay separate rows. An older file that kept growing with more than 5% of its uuids missing from the newer one is therefore a fork. Ancestors attach to their newest descendant leaf; the visible row of a group is its most recently used member, shown with `+N` after the time; `E` shows every member, older ones dimmed with `copy of <short id>`. A lineage counts as starred if any member is starred and `s` toggles all members; hide (`x`) and `Enter`/`r`/`f`/`n`/`c`/`o` act on the visible member only. Activity and live state of any member show on the visible row. Codex and OpenCode rows are never grouped. Limit: an ancestor with fewer than about 8 sketch values inside the descendant's cut-off (tiny ancestor, huge descendant) is not detected directly, only through an intermediate copy.
- Sessions outlive ccview. Every embedded session is a child of the session host daemon (`ccview-rs host`), started detached (setsid, log in the runtime dir) the first time a session is launched and not running. Quitting, a crash or a panic leaves sessions running (the panic hook only restores the terminal); a session ends when the harness itself exits or when the owner stops it with `d` (see Dismiss and stop). The protocol's only signalling message is `Request::Stop` (SIGTERM to that session's child); the debug CLI (`host --list`) has no stop command.
- Detach (`^Space x`/`d`) removes the pane from the strip for this run and says so in a notice; the session keeps running and comes back on `r` of its list row (matched by session id or pid) or at the next start. Dismissing an exited session (any key) is the only thing that removes a session from the daemon, and the daemon refuses to dismiss a running one.
- On startup ccview attaches every session the daemon lists (including exited ones, which show their final screen with the exited state) instead of attaching lazily on selection: attaching is what feeds the strip state, bells and titles, and `resize_all` resizes every session anyway.
- The daemon exits by itself after `IDLE_EXIT` (60 s) with no live session and no connected client; it never kills anything when it exits. The only other exit is the tests-only `CCVIEW_HOST_OWNER_PID` lifeline above, which does tear its sessions down.
- The PTY has one size: the active client's (the lease holder's attach or resize). Reattach first replays the daemon's scrollback (`host::history`, plain SGR rows, capped at 4 MiB cut at a row boundary, skipped on the alternate screen) and then restores the screen as vt100 `state_formatted()` (visible grid, cursor, colours, input modes), all under one parser lock so nothing is lost or repeated; the client then starts at the bottom and scrolls up into that history plus the kitty keyboard stacks, focus reporting, synchronized output and title from the `ModeSnapshot`.
- Restore after reboot. The host keeps a durable list, `sessions.json` in the state dir (not the runtime dir, which a reboot wipes), written atomically on spawn, on session-id binding and on removal. It never holds environment variables. A session whose harness exits while the host is alive is removed from the list once the exit has been seen for `EXIT_GRACE` (1 s); the grace exists because at a machine shutdown the children can die a moment before the host's signal handler runs. SIGTERM and SIGHUP set a shutting-down flag that the host loop checks before it reaps anything; it then drops entries without a session id, writes the list and exits, so exits during shutdown keep their entries. A crashed host leaves the file as it was; a starting host loads the file and keeps entries it has not restored. The session id of a Claude session is bound host-side from `<claude config>/sessions/<child pid>.json` (checked every 500 ms, also after a resume, which may assign a new id); Codex and OpenCode have no pid lookup, so only a session launched with a known id (resume) is restorable, a new one is dropped at shutdown. The launch kind is inferred from the argv (`attach`, `fork`, `resume`, `continue`, else `new`) and is informational. `ccview-rs host --restore` connects to or starts the host (detached, as for any launch) and sends `Request::Restore`: for each entry without a live owner it relaunches the harness's own resume command (`--resume <id>`, `codex resume <id>`, `opencode --session <id>`; never a prompt) in the entry's cwd with the stored absolute program, the normal Claude launch environment (agent view setting, identity variables removed) built from the host's environment and a `PATH` that starts with `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.cargo/bin`. At most `MAX_RESTORED` (12) start; entries with no session id, a missing cwd or a missing program are skipped and logged; a session id that already runs is not started again, so running `--restore` twice starts nothing the second time; concurrent `Restore` requests are serialized by a guard in the host, the second waits for the first. Afterwards the list holds the sessions that are running plus the entries that were not restored (over the cap, missing cwd or program, failed spawn), which stay for a later restore; entries without a session id and entries whose session id already runs are dropped. A `sessions.json` that cannot be parsed is renamed to `sessions.json.bad` (one kept) when the host starts, so the next write cannot overwrite it. Restored sessions are ordinary host sessions, attachable like any other.
- Unreachable host. The host compares `host.lock`, `host.sock` and `host.pid` at their paths with what it holds every `HEAL_INTERVAL` (500 ms): a missing or replaced socket is bound again (0600) and `host.pid` rewritten; a replaced or removed lock is re-taken when nobody holds the file at the path; when another host holds it, the host exits if it has no sessions and otherwise keeps them and leaves the directory alone (it can no longer be reached by name). `HostClient` never starts a daemon while `host.lock` is held; if the lock is held and the socket does not answer for `LOCKED_GRACE` (500 ms) it fails with `HostUnreachable` instead of waiting `START_TIMEOUT`. The UI shows `session host unreachable (lock held by pid N, no socket)...` in the footer (persistent, after a transient notice, until a launch succeeds; checked at startup and after a failed launch, not polled) and a launch (`r`, `y` on `live elsewhere`, `n`, `c`) starts nothing. See Recovering an unreachable host.
- Autostart is a macOS LaunchAgent (`dev.ccview-rs.host`: `ProgramArguments` = the resolved current executable, `host`, `--restore`; `RunAtLoad` true, no `KeepAlive`; stdout and stderr to `<state>/ccview-rs/host.log`; `EnvironmentVariables` only `PATH`), loaded with `launchctl bootstrap gui/<uid>` and removed with `launchctl bootout`. The `--restore` job is a short-lived client, not the host itself, so `autostart off` never kills running sessions. The settings row "Restore sessions after reboot" shows whether the plist exists and toggles `autostart on`/`off`; on other platforms it says `autostart is macOS only`.
- PLANNED (the owner's open requests, not in the code): the rest of the Rust conventions restructure (the remaining dependency-direction violations listed under Layout and style).

## Recovering an unreachable host

Symptoms: every session says `live elsewhere`, `y` (run here instead) does nothing, the footer says `session host unreachable (lock held by pid N, no socket)` (or `lock held` when the pid is unknown). The host and the sessions in it are alive; only the socket path is gone (measured once: hosts started 2026-11-10 with their socket still open but `host.sock` and `host.pid` unlinked, `host.lock` replaced by a second host). Hosts older than the self-heal above do not repair themselves.

1. Find the host: `ps -axo pid,ppid,lstart,command | rg 'ccview-rs host'` (the pid in the notice, or the content of `host.lock`, when present). The stranded sessions are its children: `ps -axo pid,ppid,command | awk '$2 == <host pid>'`. There may be two hosts in one directory.
2. The sessions cannot be attached while the socket is missing. Restarting a host ends every session in it (the children die with the PTY master); do it only after the owner agreed: send SIGTERM to the host, which keeps the durable list `sessions.json` and removes its own files, then run `ccview-rs host --restore`.
3. `host --restore` relaunches only what `sessions.json` holds: at most 12, only entries with a session id, and the list can be empty or hold fewer sessions than were running (two hosts share the one file and overwrite each other). Sessions it does not relaunch are resumed per row with `r` in the UI.
4. A host with this change repairs a deleted socket by itself within 500 ms; no manual step is needed.

## Known limitations

Verified in code:
- The unreachable-host notice is computed at startup and after a failed launch, so it stays until a launch succeeds and is not cleared when a host heals itself meanwhile. Hosts started before the self-heal (old code keeps running after a UI update) never repair their files.
- The self-restart replaces only the UI process. The session host daemon is not updated: running hosts keep their old code until a host restart (a host-side fix needs one), and the UI talks to them with the new protocol code. UI state beyond the fields in `ui_state.json` is lost on a restart (open overlays are never open then; typed-but-unsent text lives in the host's sessions and survives). The restart was verified with a fake replacement binary in a PTY test and not with a real `cargo install` over a running UI; a build that changes the host protocol is not guarded.
- Reattach carries up to 4 MiB of scrollback (the newest rows when the daemon holds more) but not what is behind an alternate screen: the main screen is unreachable while the child is on the alternate screen (vt100 exposes only the alternate grid there). The history is replayed eagerly on every attach, so a session started with many panes costs about 0.1-0.7 MB per attached session at startup (measured on synthetic content, not with real Claude). Loading history lazily on scroll was judged not feasible: vt100 cannot prepend rows to a live parser.
- A standby pane does not draw the child at all (its mirror would have the wrong geometry); it still receives the output stream. Demotion reaches the client within one output poll (200 ms), the daemon ignores its input meanwhile. Two simultaneous attaches can take the lease in one order and resize the PTY in the other. There is no protocol version: an old daemon never sends `Demoted` and enforces no lease, so a new client against it behaves as before (two active clients); an old client against a new daemon is demoted without knowing it (its input is dropped, its pane keeps drawing the mirror).
- A session whose host dies (daemon killed or crashed) is shown as exited with `host lost`; the children die with it because the PTY master closes. There is no protocol version: replacing the binary while a daemon runs leaves the old daemon serving the new client.
- A detached session without a list row (no registry match, for example a new Codex session) is reachable again only at the next start.
- Daemon-side unix sockets limit the runtime dir path to the platform `sun_path` size (104 bytes on macOS).
- OSC 8 hyperlinks are not rendered or clickable in embedded panes (only URLs visible as text are; the link target of an OSC 8 sequence with non-URL text is lost); `responder.rs` ignores unknown OSC sequences (only OSC 9;4 progress is recognised and dropped).
- Synchronized output (mode 2026) is tracked and reported to the child but output is not buffered by it; `PtyHost::synchronized_output()` is only exercised by `tests/terminal_protocol.rs`, not by drawing.
- External terminal launch is macOS only (`harness/external_terminal.rs`).
- Unix only (`libc`, `os::unix`).
- crossterm is built with its `use-dev-tty` feature, which swaps its default mio event source for a `poll`-based one (`select` on macOS, through `filedescriptor`, already a dependency of `portable-pty`). The default source loses keys typed in the same instant as a resize: `crossterm-0.29.0/src/event/source/unix/mio.rs` `try_read` returns the `Resize` from the SIGWINCH token and drops the TTY token of the same batch, and mio registers with `EV_CLEAR` (edge-triggered), so the bytes waited for the next key (measured in `tests/resize_input_pty.rs`: 129 of 300 rounds before, 0 of 900 after; upstream crossterm issue 1126, unreleased fixes in PRs 1128 and 1154). Calling `event::poll(Duration::ZERO)` after a `Resize` does not help (measured 41 of 100), because the edge is already consumed. With `use-dev-tty`, `event::poll(Duration::ZERO)` always returns false (upstream issue 839); ccview only calls `event::read` and `supports_keyboard_enhancement`, which polls with a 2 s timeout. When a crossterm release fixes issue 1126 the feature can be dropped. `session_host_pty.rs` still waits for the harness to report the new size before typing; that wait was the workaround for this and is kept.
- The Claude daemon check and `claude agents --json` depend on a Claude version that has them; absence yields no agent badges rather than an error.
- Stale is a heuristic on file mtime: a long tool call that writes nothing to the transcript (a 40 minute test run) looks the same as a stuck session; sub-agent output is not the parent transcript, which is why running agents suppress the marker. The registry's `updatedAt` was not shown to change during a busy turn (only idle sessions were available to read), so the transcript mtime is the signal that matters.
- `asks you` is a heuristic over the assistant's prose (see Product decisions): it was measured against the structure of one real transcript only (`end_turn` text, `stop_hook_summary`, `turn_duration`, `away_summary` as the last records), never against a labelled set, so its false-positive and false-negative rates are unknown. A transcript line that merely contains the byte strings `"type":"user"` or `"tool_result"` is classified by those markers without a full parse, like the recency scan.
- Shared checkout is a path heuristic: two sessions in different subdirectories of one repository are flagged although they may touch disjoint files; sessions in two clones of one repository, or in a worktree and the checkout it came from, are not. The per-cwd cache is kept while a session with that cwd runs, so a `git init` made after the session started is not noticed until the session ends. The key comes from the registry's `cwd`, which is the directory the session started in, not where it has `cd`-ed since.

Not verified:
- The peer-uid rejection path (it needs a second user), and the Linux `SO_PEERCRED` branch (only the macOS `getpeereid` branch was compiled and run).
- Real Claude behaviour across a reattach (fake harnesses only).
- Claude `cwd` fallback: when a transcript has no `cwd` field, `cwd_from_project_dir` turns every `-` of the project directory name into `/`, so a directory such as `my-proj` derives a path that does not exist; launches then refuse with `directory not found: <path>` (the check is in `App::launch`) instead of starting elsewhere. The derivation itself is not fixed.
- Claude embedded behaviour past the trust dialog: no test goes beyond a fake binary.
- `tests/terminal_protocol.rs` flaking under load: one run under CPU load did not complete in the time available, so it is neither confirmed nor ruled out; it passed in the normal runs.
- Real Codex and OpenCode launch behaviour beyond argv: tested with fake binaries only.
- Restore after reboot: not tested across a real reboot, with a real `launchctl bootstrap`, or with the real login `PATH`; the shutdown race is covered by the 1 s exit grace, not by a measured system shutdown. Real Claude's registry file and resume behaviour were not exercised (fake harness only).
